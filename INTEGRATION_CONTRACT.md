# Город без света — контракт интеграции

**Статус: версия Godot, структура/владельцы и MVP согласованы пользователем.** Точные интерфейсы ниже зафиксированы архитектором как целевой контракт первой реализации: они ещё не реализованы и не проверены в работающем проекте. Изменения публичных интерфейсов, ID или формата сохранения предварительно согласуются с архитектором и владельцами затронутых модулей. Не подключайте невидимые другим чатом самодельные аналоги.

[Архитектура](PROJECT_ARCHITECTURE.md) · [Задачи, владельцы файлов и проверки](TASKS.md)

## 1. Общие правила

- Сигналы и методы ниже — **предлагаемый API игры**, а не встроенные методы Godot. Параметры перечислены в порядке передачи. `bool` сообщает об успешном выполнении, а не об игровой победе.
- Корневой узел сцены — её публичный интерфейс. Внутренние дочерние узлы другой команды не искать и не менять. Исключения — публичные пути `Main` и `World`, перечисленные ниже.
- Публичные ID передаются как `String`. Неподдерживаемый ID, неправильные данные или повторный запуск не должны приводить к падению и частичному изменению состояния.
- Инициатор создаёт экземпляр, подключает сигналы, добавляет узел в дерево и только потом вызывает его метод запуска. При неудаче он освобождает экземпляр и восстанавливает предыдущий режим. На одно открытие/столкновение выдаётся максимум один завершающий сигнал.
- `Main` — единственный координатор режимов. Никакой модуль не открывает чужую сцену и не обращается к `Main` по абсолютному пути. Управление идёт через сигналы и вызовы корня сцены.
- В проектных путях `res://` находятся только ресурсы для чтения. Файл сохранения живёт в `user://`. Данные в сохранении — обычные JSON-значения, не объекты `Node`, `Resource` или `Vector2`.

## 2. Главная сцена и жизненный цикл

**Владелец:** интегратор. Пути `res://scenes/main/main.tscn`, `res://scripts/main/main.gd`. Согласованное дерево после интеграции:

```text
Main (Node)
├── WorldHost (Node2D)
├── StoryDirector (Node, экземпляр scenes/story/story_director.tscn)
└── Overlay (CanvasLayer)
    └── UIRoot (Control)
        ├── BattleHost (Control)
        ├── DialogueHost (Control)
        ├── EndingHost (Control)
        └── Status (Label)
```

`WorldHost` содержит один экземпляр мира; хосты интерфейса — не более одного соответствующего активного экземпляра. Сцены боя, диалога и концовки имеют корневой тип `Control`. `UIRoot` и хосты занимают viewport; `UIRoot`, хосты и `Status` не перехватывают мышь (`mouse_filter = Control.MOUSE_FILTER_IGNORE`), иначе пустой верхний хост может закрыть кнопки другого. Кнопки внутри активной сцены сохраняют собственную обработку мыши. При открытии диалога, боя или концовки его первая доступная кнопка получает фокус (`grab_focus()`), чтобы можно было управлять клавиатурой. В MVP только один режим: **исследование**, **диалог**, **бой** или **концовка**. Режим хранит `Main`, в сохранение он не попадает.

1. Новый запуск: `GameState.reset_new_game()`, создать мир, включить исследование. Отображать назначенные клавиши.
2. На `dialogue_requested`: сразу запретить ввод мира, создать диалог, подключить `choice_selected` и `dialogue_finished`, вызвать `start_dialogue`. Выбор передать `StoryDirector.apply_choice`; при `false` сообщить, что выбор недоступен или уже сделан. При завершении удалить диалог и снова включить мир. При неуспешном старте показать `Status` и восстановить исследование. Отмена без выбора разрешена.
3. На `battle_requested`: запретить ввод и скрыть мир, создать бой, подключить `battle_finished`, вызвать `start_encounter(id, GameState.get_party())`. При результате вызвать `StoryDirector.record_battle_result`, удалить бой, показать тот же мир и включить ввод. Ошибка старта также возвращает видимость и ввод мира.
4. На `exit_requested`: запросить `StoryDirector.resolve_ending`. Пустая строка означает, что условия не выполнены: показать понятную подсказку и остаться в мире. Иначе запретить ввод мира, создать экран концовки и вызвать `show_ending`. При ошибке старта восстановить мир. По `restart_requested` закрыть экран, вызвать `GameState.reset_new_game()` и `World.reset_player_position()`, затем включить мир.
5. F2/F3 обрабатываются только при исследовании. При неудачном сохранении/загрузке показать сообщение; текущие состояние и позиция не меняются. Перед загрузкой проверить данные и `World.can_restore_player_position`; при необходимости сохранить прежний снимок для отката. Восстановление и установка позиции выполнять последовательно без ожидания кадра; при неожиданном отказе установки позиции восстановить прежний снимок.

До подключения каждого модуля интегратор не создаёт в основной сцене ссылку на отсутствующий файл. Промежуточная версия основы обязана запускаться сама по себе; полностью собранный игровой цикл появляется только после задач интеграции.

## 3. `GameState`: общие факты

**Владелец:** чат состояния. Будущий скрипт `res://scripts/core/game_state.gd`, `extends Node`; интегратор регистрирует его автозагрузкой с именем `GameState` **после** появления файла. Это имя автозагрузки не дублируется через `class_name`. Другие модули пользуются методами, не изменяют внутренние словари и массивы.

| Предлагаемый сигнал/метод | Поведение |
|---|---|
| `signal state_changed()` | После успешного изменения; не выдаётся при обычной операции без изменения. |
| `reset_new_game() -> void` | Флаги и отношения пустые, группа `['hero']`; один `state_changed`, даже если состояние уже начальное. |
| `get_flag(id: String) -> bool` | Неизвестный флаг равен `false`. |
| `set_flag(id: String, value: bool) -> void` | Непустой ID; изменение фиксируется и вызывает сигнал. Пустой ID игнорируется. |
| `get_relation(id: String) -> int` | Отношение к NPC/группировке, по умолчанию `0`. |
| `change_relation(id: String, delta: int) -> int` | Для непустого ID добавить `delta`, ограничить результат диапазоном от `-100` до `100`, вернуть итог. Сигнал только при изменении. Пустой ID не изменяет данные и возвращает `0`. |
| `get_party() -> Array[String]` | Вернуть отдельную копию упорядоченного состава. Первым всегда `hero`. |
| `add_party_member(id: String) -> bool` | Добавить непустой отсутствующий ID; `false` для пустого или уже присутствующего, включая `hero`. Нет дубликатов. |
| `export_state() -> Dictionary` | Глубокая копия данных в формате ниже; изменение копии не меняет игру. |
| `import_state(data: Dictionary) -> bool` | Полностью проверить данные до изменения; при успехе заменить состояние и испустить один `state_changed`, при ошибке не менять ничего. |

Форма `export_state` и `import_state`:

```json
{
  "flags": {"story.mira.helped": true},
  "relations": {"npc.mira": 1},
  "party": ["hero", "companion.mira"]
}
```

Все три поля обязательны. `flags` — непустые строковые ключи и булевы значения; `relations` — непустые строковые ключи и целые значения `-100…100`; `party` — массив непустых неповторяющихся строк, первый элемент `hero`. Отсутствие флага или отношения имеет значения по умолчанию выше. Числа, прочитанные из JSON, могут быть `float`: принять конечное число только если оно целое и находится в диапазоне, затем безопасно привести к `int`. Не считать отдельную переменную «добро/зло» источником истины: конкретные решения хранятся как флаги, а отношения — по ID персонажа или группировки.

## 4. `SaveService`: один слот

**Владелец:** чат состояния. Скрипт `res://scripts/core/save_service.gd`, `extends Node`; после появления скрипта интегратор регистрирует автозагрузку `SaveService`. Сервис не знает об узлах, не вызывает `GameState` и не восстанавливает игру сам.

| Предлагаемый метод | Поведение |
|---|---|
| `save_game(snapshot: Dictionary, path: String = "user://save_v1.json") -> int` | Проверить форму и записать JSON. `OK` (`0`) — успех; другое значение — код ошибки Godot. При ошибке не менять состояние игры. |
| `load_game(path: String = "user://save_v1.json") -> Dictionary` | Вернуть `{"ok": bool, "data": Dictionary, "error": String}`. При успехе `data` содержит снимок, `error` пуст; при ошибке `data` пуст и `error` объясняет проблему. Никаких изменений состояния. |

По умолчанию это один игровой слот. Необязательный путь нужен тестам: они используют отдельный `user://save_test_v1.json` и его временные файлы, не затирая игровой слот. Запись разрешается только в `user://`; основной вызов не передаёт другой путь.

```json
{
  "version": 1,
  "world": {
    "id": "world.demo",
    "player_position": {"x": 80.0, "y": 80.0}
  },
  "game_state": {
    "flags": {"story.mira.helped": true},
    "relations": {"npc.mira": 1},
    "party": ["hero", "companion.mira"]
  }
}
```

Это пример формы, а не существующий файл или гарантия, что конкретные координаты допустимы на будущей карте. Обязательны версия `1`, словари `world` и `game_state`, строковый ID мира, конечные числовые `x` и `y`, а также данные состояния из раздела 3. На чтении проверять целостность структуры, типы и поддерживаемую версию, в том числе целочисленные JSON-числа как описано выше. Неподдерживаемую версию не переписывать и не мигрировать молча. `Main` дополнительно проверяет ID загруженного мира и допустимость позиции; `GameState.import_state` атомарно проверяет внутренние данные.

Не затирать единственный хороший слот при ошибке проверки или записи: писать во временный файл рядом со слотом, закрывать его и только затем заменять слот с сохранением резервной копии. Резервную копию не удалять до успешной замены; при ошибке восстановления сообщить, где она находится. Поведение файловой системы при сбое питания различается, поэтому абсолютная атомарность не обещается. Тесты отдельно проверяют отсутствующий, повреждённый и несовместимый файл и отказ записи.

## 5. Мир, игрок и взаимодействия

**Владелец:** чат мира. Сцена `res://scenes/world/test_map.tscn`, корень `World` типа `Node2D`, скрипт `res://scripts/world/test_map.gd`. Игрок — `scenes/world/player.tscn` (`CharacterBody2D`), интерактивная цель — `scenes/world/interactable.tscn` (`Area2D`). Рекомендуемое внутреннее дерево, где перечисленные имена и типы — публичные для этой сцены:

```text
World (Node2D)
├── Terrain (TileMapLayer)
├── Player (CharacterBody2D)
│   ├── Sprite2D
│   ├── CollisionShape2D
│   └── InteractionArea (Area2D)
│       └── CollisionShape2D
└── Interactables (Node2D)
    ├── Mira (Area2D)
    ├── BattleTrigger (Area2D)
    └── Exit (Area2D)
```

Для столкновений: слой 1 — препятствия мира, слой 2 — тело игрока, слой 3 — зоны взаимодействия. Тело игрока проверяет слой 1. `InteractionArea` отслеживает слой 3 (`monitoring`), а цели доступны для обнаружения (`monitorable`); у обеих сторон есть формы столкновения. Движение обрабатывается в физическом цикле и учитывает `set_exploration_enabled`; при выключении текущая скорость сбрасывается. Клавиша взаимодействия не работает вне исследования.

Интерактивная зона использует скрипт `res://scripts/world/interactable.gd`, при необходимости с единственным глобальным `class_name WorldInteractable`. Она предоставляет экспортируемые `kind: String` и `target_id: String`, метод `interact() -> void` и сигнал `activated(kind: String, target_id: String)`. Допустимые виды: `dialogue`, `battle`, `exit`. Игрок при E выбирает одну доступную цель: ближайшую по расстоянию; при равном расстоянии — по строковому пути узла. Он вызывает только её `interact()`. Мир получает `activated` и переводит его в соответствующий сигнал ниже. Не создавать прямые зависимости мира от диалога или боя.

| Сигнал/метод корня `World` | Контракт |
|---|---|
| `signal dialogue_requested(dialogue_id: String)` | Интерактивная цель просит открыть диалог. |
| `signal battle_requested(encounter_id: String)` | Запрос на бой. |
| `signal exit_requested(exit_id: String)` | Запрос на завершение истории. |
| `get_world_id() -> String` | Для тестовой карты всегда `world.demo`. |
| `set_exploration_enabled(enabled: bool) -> void` | Включить/выключить движение и взаимодействие игрока. |
| `get_player_position() -> Vector2` | Позиция игрока в локальных координатах корня `World`; в JSON Main отдельно записывает `x` и `y`. Все методы позиции ниже используют ту же систему координат. |
| `can_restore_player_position(position: Vector2) -> bool` | Позиция конечна, находится в проходимой области карты и форма игрока не попадает в препятствие. |
| `set_player_position(position: Vector2) -> bool` | При допустимой позиции переместить и обнулить скорость; иначе вернуть `false` без изменения позиции. |
| `reset_player_position() -> void` | Вернуть игрока в безопасную стартовую точку и обнулить скорость. |

Для простого MVP допускается карта с открытой внутренней областью и стенами по краям: это упрощает проверку допустимой позиции. При добавлении внутренних препятствий владелец мира расширяет проверку. Изображения персонажа и клетки привязаны к сетке 16 × 16, но движение не обязано быть строго пошаговым по клеткам.

## 6. Диалог

**Владелец:** чат диалогов. `res://scenes/ui/dialogue_box.tscn` (`Control`), скрипт `res://scripts/dialogue/dialogue_box.gd`, данные `res://data/dialogues/mira_intro.json`.

| Сигнал/метод корня | Контракт |
|---|---|
| `start_dialogue(dialogue_id: String) -> bool` | После добавления сцены в дерево открыть известный валидный диалог. При ошибке вернуть `false` и не испускать сигналов. Повторный старт активного экземпляра запрещён. |
| `signal choice_selected(dialogue_id: String, choice_id: String)` | При выборе испускается не более раза и **до** `dialogue_finished`. |
| `signal dialogue_finished(dialogue_id: String)` | Ровно один раз после выбора или отмены. Отмена не испускает `choice_selected`. |

Диалоговая сцена отображает текст и отдаёт ID; она **не** пишет флаги, отношения или состав группы. Кнопки и `ui_accept`/`ui_cancel` обрабатывает сама сцена, пока мир выключен. Для MVP известен один ID, сопоставленный с конкретным путём, а не с путём, построенным из произвольного ввода:

```json
{
  "id": "dialogue.mira_intro",
  "speaker": "Мира",
  "text": "Поможешь мне добраться до убежища?",
  "choices": [
    {"id": "choice.mira.help", "text": "Помочь Мире"},
    {"id": "choice.mira.refuse", "text": "Идти одному"}
  ]
}
```

Текст здесь примерный; обязательны форма, непустые строки, два разных ID и проверка входных данных. Сцена не запускается с отсутствующим/повреждённым JSON. Диалог с несколькими репликами, локализация и редактор ветвлений потребуют отдельного расширения контракта, а не негласного изменения формы.

## 7. Бой

**Владелец:** чат боя. `res://scenes/combat/battle.tscn` (`Control`), `res://scripts/combat/battle.gd`, данные `res://data/combat/street_01.json`. Самостоятельная сцена: она получает ID столкновения и копию группы, не обращается к `GameState`, миру или `Main`.

| Сигнал/метод корня | Контракт |
|---|---|
| `start_encounter(encounter_id: String, party: Array[String]) -> bool` | Запускает одно известное валидное столкновение, если первым в группе стоит `hero`, участников нет в двух экземплярах, все ID поддерживаются и данные корректны. В MVP поддерживаются только `hero` и `companion.mira`. Иначе `false`, без сигнала. Повторный старт активного экземпляра запрещён. |
| `signal battle_finished(encounter_id: String, result: String)` | Ровно один раз после успешного старта: `result` — `victory` или `defeat`. |

MVP: предсказуемый бой без случайностей. Игрок выбирает **атаку** или **пропуск**. Атака героя уменьшает здоровье врага; если враг жив и в группе есть `companion.mira`, Мира автоматически атакует; если враг ещё жив, он атакует героя. Здоровье врага `<= 0` — победа сразу; здоровье героя `<= 0` — поражение. После поражения состояние истории не ухудшается, можно начать столкновение заново; при каждом новом бою здоровье восстанавливается из данных. Временное здоровье в сохранение MVP не попадает, предметов и побега в бою нет.

```json
{
  "id": "encounter.street_01",
  "actors": {
    "hero": {"max_hp": 6, "attack": 2},
    "companion.mira": {"max_hp": 4, "attack": 1}
  },
  "enemy": {"id": "enemy.raider", "max_hp": 6, "attack": 2}
}
```

Все характеристики — положительные целые числа, проверенные и приведённые из JSON. Враг для простоты атакует только героя. Герой может победить и один, и с Мирой; многократный пропуск позволяет проверить поражение. Повторный клик во время завершения не выдаёт второй результат. Неизвестный участник или повреждённые данные приводят к безопасному отказу запуска. Позднее баланс, цели и действия расширяются через новый согласованный контракт.

## 8. История и концовки

**Владелец:** чат истории. `res://scenes/story/story_director.tscn` (корень `Node`), `res://scripts/story/story_director.gd`; экран `res://scenes/ui/ending_screen.tscn` (корень `Control`), `res://scripts/story/ending_screen.gd`. `StoryDirector` не хранит вторую копию флагов и не открывает сцены.

| Метод `StoryDirector` | Контракт |
|---|---|
| `apply_choice(dialogue_id: String, choice_id: String) -> bool` | Применить известный, ещё не сделанный выбор через `GameState`, вернуть `true`. Неизвестный или уже зафиксированный выбор — `false`, без повторных последствий. |
| `record_battle_result(encounter_id: String, result: String) -> void` | Для победы в известном столкновении записать флаг; поражение и неизвестные значения не меняют состояние. |
| `resolve_ending(exit_id: String) -> String` | Вернуть известный ID концовки или пустую строку, если условия не выполнены/данные противоречивы. Без изменения состояния. |

Точный демонстрационный смысл:

- `dialogue.mira_intro` + `choice.mira.help`: установить `story.mira.helped`, изменить `npc.mira` на `+1`, добавить `companion.mira`.
- `dialogue.mira_intro` + `choice.mira.refuse`: установить `story.mira.refused`, изменить `npc.mira` на `-1`; спутник не добавляется.
- Если любой из двух флагов выбора уже установлен, повторный выбор ничего не делает. Флаг выставляется до прочих последствий, чтобы повторный вызов не начислил их снова.
- `encounter.street_01` + `victory`: установить `combat.street_01.victory`. При `defeat` новый флаг не выставляется и ранее полученная победа не стирается.
- Для `exit.demo` нужны победа и **ровно один** флаг выбора. При помощи вернуть `ending.shelter_together`, при отказе — `ending.shelter_alone`. Если выбор отсутствует или оба флага установлены, вернуть пустую строку.

Экран концовки предоставляет `show_ending(ending_id: String) -> bool` и `signal restart_requested()`. Он знает оба ID и показывает соответствующие короткие тестовые тексты и кнопку начала заново. Неизвестный ID даёт `false` без сигнала. `Main` обрабатывает перезапуск; сам экран не меняет `GameState`.

## 9. Реестр ID для первой интеграции

| Где задано | ID | Кто использует |
|---|---|---|
| Мир | `world.demo` | `Main`, сохранение |
| Интерактивная Мира | `dialogue.mira_intro` | Мир → `Main` → диалог/история |
| Выборы | `choice.mira.help`, `choice.mira.refuse` | Диалог → история |
| Отношение | `npc.mira` | История → `GameState` |
| Участники | `hero`, `companion.mira` | Состояние → бой |
| Столкновение и враг | `encounter.street_01`, `enemy.raider` | Мир → бой; результат → история |
| Выход | `exit.demo` | Мир → история |
| Концовки | `ending.shelter_together`, `ending.shelter_alone` | История → экран концовки |
| Флаги | `story.mira.helped`, `story.mira.refused`, `combat.street_01.victory` | История → состояние |

Чат мира выставляет эти значения в соответствующих интерактивных зонах: `dialogue`/`dialogue.mira_intro`, `battle`/`encounter.street_01`, `exit`/`exit.demo`. Одно и то же значение не нужно вручную дублировать в нескольких менеджерах.

## 10. Экспорт, проверка и изменения контракта

Диалог и данные боя — обычные JSON-файлы, читаемые в будущей реализации через `FileAccess`. При настройке экспорта интегратор обязан включить `*.json` в фильтр экспорта нересурсных файлов и проверить именно собранную игру; успешный запуск из редактора этого не доказывает. Сохранения в `user://` не включаются в пакет и Git. Подробности подтверждены официальными справочниками [FileAccess](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/FileAccess.xml) и [экспорта Godot 4.4](https://github.com/godotengine/godot-docs/blob/4.4/tutorials/export/exporting_projects.rst).

Если потребуется новый сигнал, тип действия, участник группы, поле сохранения или изменение владельца файла: 1) описать проблему и затронутые пути; 2) предложить совместимое изменение и, для сохранения, миграцию версии; 3) получить согласование архитектора и владельцев; 4) обновить контракт и только после этого связывать код. Каждый PR сообщает версии интерфейса/базы, проверку и что должен сделать следующий интегратор.
