# Город без света — проект технической архитектуры

**Статус: версия Godot, структура/владельцы и состав MVP согласованы пользователем.** В задаче BASE-01 создана основа проекта; игровые модули пока не реализованы. Автор и ответственный за архитектуру и контракты — главный технический архитектор. База первоначального анализа: `main`, коммит `44ed3e3`, когда в репозитории был только минимальный `README.md`. Имена ещё не созданных игровых файлов и API ниже — целевые, а не существующие.

- [Контракт интеграции](INTEGRATION_CONTRACT.md) — целевые имена узлов, методов, сигналов, ID и форматов для первой реализации.
- [Задачи и порядок работы](TASKS.md) — ответственные, конкретные файлы, зависимости и проверки.
- `docs/ARCHITECTURE.md`, `docs/CONTRACTS.md` и `docs/TASKS.md` — указатели для командных инструкций, требующих именно эти пути. Единственные исходные документы — три файла в корне; не ведите вторые копии.

## 1. Что мы создаём

Одиночная 2D RPG с видом сверху: исследование современного города после катастрофы, пошаговые бои, диалоги, спутники, морально неоднозначные решения и несколько концовок. Игрок не получает обязательную метку «добро» или «зло»: история хранит конкретные решения и их последствия. Художественное содержание примера ниже временное и не определяет окончательный сюжет.

Архитектурные принципы:

1. Одна общая игра и один репозиторий, а не отдельный проект для каждого чата.
2. Сцены самостоятельны, а главная сцена связывает их сигналами. Она не содержит логику всех систем.
3. Один источник общих фактов и один сервис сохранения. Не создаём параллельные менеджеры того же состояния, универсальную шину событий или плагины без необходимости.
4. Данные, созданные модулем, меняет его владелец через оговорённый интерфейс; чужие скрипты и сцены не редактируются молча.
5. Сначала работающий небольшой игровой цикл, затем контент и расширения. Простая временная графика допустима, но перемещение, выбор, бой и сохранение должны действительно работать.

## 2. Техническая основа

**Согласованная базовая версия команды:** Godot **4.4.1-stable**, обычная версия с GDScript, без обязательных сторонних плагинов. Пользователь подтвердил эту версию в рамках требования Godot 4.x. Её точная версия и приведённые ниже имена встроенных настроек/методов сверены с официальным исходным справочником Godot. Фактически выполненные проверки основы и их ограничения перечислены в [TASKS.md](TASKS.md).

При создании основы интегратор настраивает:

| Настройка | Предлагаемое значение |
|---|---|
| Базовый viewport | 640 × 360 |
| Renderer | Compatibility (`gl_compatibility`) |
| Stretch Mode / Aspect / Scale Mode | `viewport` / `keep` / `integer` |
| Default Texture Filter | Nearest |
| Ячейка карты и базовый спрайт персонажа | 16 × 16 пикселей |
| Основная сцена | `res://scenes/main/main.tscn` |

При целочисленном масштабировании окно меньше 640 × 360 может обрезать изображение. Для настольного запуска предлагается задать минимальный размер окна 640 × 360 из `Main` через `get_window().min_size = Vector2i(640, 360)` и проверить изменение размера вручную. Рендерить с целочисленным масштабом не означает запрещать изменение размера окна: при несовпадающих пропорциях возможны поля.

Зарегистрировать в Input Map действия `move_up`, `move_down`, `move_left`, `move_right`, `interact`, `save_game`, `load_game`. Начальная раскладка: WASD и стрелки — движение, E — взаимодействие, F2/F3 **в окне игры** — сохранить/загрузить. Для элементов интерфейса используются стандартные действия `ui_accept`, `ui_cancel` и навигация Godot. В диалоге, бою и на экране концовки движение и взаимодействие в мире заблокированы; один нажатый ввод не должен открывать несколько сцен.

## 4. Имена и соглашения

- Каталоги, файлы и функции: английский `snake_case`, например `test_map.tscn`, `apply_choice()`.
- Узлы сцены: `PascalCase`, например `WorldHost`, `DialogueHost`. Публичные пути узлов из контракта менять только вместе с интегратором и архитектором.
- `class_name`, если он действительно нужен: уникальный `PascalCase`, например `WorldInteractable`. Не задавать автозагрузке `class_name` с тем же именем, что у её singleton: это конфликт имён.
- Сигналы: `snake_case`; событие в прошедшем времени (`battle_finished`), запрос — с суффиксом `_requested` (`dialogue_requested`). Аргументы и смысл определены в контракте.
- Константы и имена enum: `UPPER_SNAKE_CASE` для значений, `PascalCase` для имени типа/enum. Ресурсы и сцены называются по содержимому, без пробелов и локальных абсолютных путей.
- Стабильные ID данных — английские строки в нижнем регистре, разделённые точками, например `dialogue.mira_intro`, `choice.mira.help`, `companion.mira`. ID не равен тексту на экране и не должен меняться при правке перевода. На границах модулей в MVP используются `String`, не ссылки на узлы из чужих сцен.
- Скрипт сцены по возможности имеет имя её корневой сцены. Локальные узлы можно менять внутри своего модуля, но согласованные публичные имена узлов, сигналов и методов — часть контракта.

## 5. Как части связаны

Предлагается ровно две автозагрузки, зарегистрированные интегратором после появления их реальных скриптов:

- `GameState` — общие флаги, отношения и состав группы. Не управляет окнами, боем или файлами.
- `SaveService` — чтение/запись снимка в `user://`. Не ищет узлы мира и не меняет `GameState` самостоятельно.

`Main` создаёт и связывает сцены, держит текущий режим и отключает ввод мира при открытии интерфейса или боя. Мир сообщает о взаимодействиях; диалог сообщает о выборе; `StoryDirector` применяет последствия через `GameState`; бой возвращает результат; `Main` возвращает игрока в мир или показывает концовку. Модель боя и временные очки здоровья живут внутри боя. Никакой системе не нужно знать внутреннее дерево другой сцены.

Согласованное будущее дерево `Main`:

```text
Main (Node)
├── WorldHost (Node2D)          # загруженный мир остаётся здесь
├── StoryDirector (Node)        # экземпляр сцены истории
└── Overlay (CanvasLayer)
    └── UIRoot (Control)
        ├── BattleHost (Control)   # активная сцена боя
        ├── DialogueHost (Control)
        ├── EndingHost (Control)
        └── Status (Label)        # подсказка/ошибка без блокировки игры
```

`Main` — единственный владелец переходов. Он не добавляет ссылки на ещё не влитые сцены: сначала каждая часть проходит самостоятельную проверку, потом интегратор подключает её. По завершении боя мир не пересоздаётся, позиция игрока остаётся прежней. Новый запуск истории сбрасывает общее состояние и возвращает персонажа на старт.

## 6. Системы и зависимости

| Система | Назначение | Зависимости и границы | Этап |
|---|---|---|---|
| Основа, ввод, интеграция | Проект, `Main`, переходы и подсказки | Godot; подключает модули по мере готовности | MVP |
| Общее состояние | Флаги решений, отношения, группа | Самостоятельно; изменения только через `GameState` | MVP |
| Сохранение | Один слот, проверка и восстановление снимка | `Main` собирает данные состояния и мира; сервис не зависит от их узлов | MVP |
| Мир и исследование | Карта, движение, коллизии, триггеры, позиция | Основа и Input Map; посылает сигналы, не запускает чужие сцены | MVP |
| Диалоги | Показ данных и выдача выбранного ID | Данные диалога; не меняет состояние истории | MVP |
| История и моральный выбор | Применение решений, условия и определение концовки | `GameState`, ID диалогов и результатов боя | MVP |
| Спутники | Членство в группе и участие в бою | Группа в `GameState`, эффекты истории, данные боя | MVP: один необязательный спутник; без следования по карте |
| Пошаговый бой | Очередь, здоровье, победа/поражение | Данные столкновения и переданный состав группы; не меняет мир напрямую | MVP |
| Интерфейс и концовки | Диалог, бой, подсказки, концовка и перезапуск | Свои сцены; переходами управляет `Main` | MVP |
| Отношения и группировки | Значения отношений и их сюжетные последствия | Хранятся в `GameState`; история использует ID `npc.*` / `faction.*` | Отношение к одному NPC — MVP; группировки — позже |
| Задания, ветвление и больше концовок | Сюжетные цепочки | Флаги/история/диалоги; новые контракты согласуются заранее | После MVP |
| Инвентарь, предметы, экипировка, развитие | Содержимое и характеристики персонажей | Потребуются согласованные схема сохранения и контракты состояния/боя | После MVP |
| Звук, музыка и настройки | Воспроизведение и пользовательские настройки | Интегратор и отдельный владелец; не требуются для первого цикла | После MVP |
| Графика, анимация, локализация | Финальные ассеты и тексты | Контракты сцен/данных; для MVP разрешены простые собственные прототипы | Постепенно |
| Проверка и сборка | Автотесты, ручной проход и экспорт | Все готовые модули; конфигурацию экспорта меняет интегратор | С каждого этапа |

Расширение таблицы не даёт право заранее придумывать API неразработанной системы: сначала владелец и архитектор согласуют изменение [контракта](INTEGRATION_CONTRACT.md), затем код и миграцию сохранений.

## 7. Минимальная рабочая версия: MVP 0.1

Одна небольшая карта с работающими столкновениями, персонажем, Мирой, противником/триггером боя и выходом. Проверяемый сценарий:

1. Игрок ходит и нажимает E возле Миры. Диалог предлагает помочь ей либо отказаться.
2. Выбор записывается один раз. Помощь меняет отношение и добавляет Миру в группу; отказ меняет отношение в другую сторону. Повторный разговор не начисляет последствия заново.
3. Игрок начинает один пошаговый бой. Герой атакует или пропускает ход; присоединившаяся Мира ходит автоматически; противник отвечает. Победа и поражение различаются. После поражения можно повторить бой.
4. После выбора и победы выход показывает одну из **двух тестовых концовок** в зависимости от решения. Без необходимых условий объясняется, что ещё нужно сделать. Экран позволяет начать заново.
5. В режиме исследования F2 сохраняет, F3 загружает единственный слот: позицию, выбор, отношения и группу. Ошибка или повреждённый файл не должны разрушать текущее состояние игры. Подсказка сообщает результат.

Это не финальный сюжет. В MVP нет обязательного инвентаря, ИИ спутника на карте, сложной системы заданий или баланса множества врагов. Они не маскируются под готовые функции. Полный порядок переходов и форматы данных заданы в контракте.

## 8. Ответственные и параллельная работа

**Единый владелец каждого файла:**

| Чат / роль | Исключительная зона | Не делает |
|---|---|---|
| Архитектор / координатор | Три корневых документа и указатели в `docs/` | Не меняет код чужого модуля без согласования |
| Интегратор | `project.godot`, файлы основы Git, `scenes/main/`, `scripts/main/`, `tests/base/`, `.github/workflows/base-01.yml`, позже `export_presets.cfg` и README по необходимости | Не переписывает модули; только подключает их по контракту |
| Состояние и сохранения | `scripts/core/`, `tests/core/` | Не правит `project.godot` и сцены мира |
| Мир и взаимодействие | `scenes/world/`, `scripts/world/`, `assets/prototype/world/` | Не открывает диалоги и бои напрямую |
| Диалоги | `scenes/ui/dialogue_box.tscn`, `scripts/dialogue/`, `data/dialogues/`, `tests/dialogue/` | Не применяет последствия выбора |
| Бой | `scenes/combat/`, `scripts/combat/`, `data/combat/`, `assets/prototype/combat/`, `tests/combat/` | Не меняет состояние и сцены мира напрямую |
| История и концовки | `scenes/story/`, `scripts/story/`, `scenes/ui/ending_screen.tscn`, `tests/story/` | Не правит состояние и диалоговые данные напрямую |
| QA | `tests/integration/`, отчёт о проверках | Не меняет чужую реализацию без согласования |
| Художественные/звуковые задачи | Соответственно `assets/art/` и `assets/audio/` | Не заменяют прототипы и ссылки в чужих сценах без согласования |

В MVP `TASKS.md` обновляет архитектор по отчётам исполнителей, чтобы параллельные ветки не конфликтовали. Новый чат получает конкретную задачу, согласованный контракт, ссылки на документы и точный коммит общей базы. Поскольку независимые чаты не видят невлитые результаты, сначала передайте им содержимое утверждённых документов или влейте эти документы в `main` решением пользователя; затем аналогично передавайте интегрированную основу. Каждый чат работает в своей назначенной платформой ветке, присылает PR и не сливает его самостоятельно.

В каждом результате/PR исполнитель перечисляет **все созданные и изменённые файлы**, зависимости и точную базу, проверенные команды/шаги и их результат, известные ошибки, требуемые изменения у других владельцев и инструкцию интеграции. Если нужного метода или сигнала нет, исполнитель описывает проблему и предлагает поправку архитектору, а не создаёт вторую несовместимую систему.

## 9. Как пользоваться планом и запустить проект: для новичка

- **Узел** — элемент сцены; **сцена** — собранный из узлов объект/экран; **скрипт** добавляет поведение. **Сигнал** сообщает о событии, не заставляя отправителя знать устройство получателя. **Автозагрузка** — один общий объект, который Godot создаёт при старте. **Контракт** — заранее согласованное обещание имён и поведения.
- В ветке BASE-01 есть `project.godot` и основная сцена. Установите Godot 4.4.1, в менеджере проектов выберите импорт этого `project.godot`, откройте проект и нажмите **F5**: появится экран основы, а не готовая игра. В отдельной готовой сцене **F6** запускает текущую сцену; это не равно запуску всей игры.
- В завершённом MVP: WASD/стрелки, E, F2 и F3. Пройдите оба варианта выбора, бой, выход и сохранение/загрузку по шагам из [TASKS.md](TASKS.md). Эти действия пока являются планом проверки, не отчётом об уже пройденном тесте.
- Пользователь подтвердил версию Godot, структуру/владельцев и маленький игровой цикл. После принятия BASE-01 передайте актуальную общую базу чатам состояния, мира, диалогов и боя; если что-то непонятно, можно попросить объяснить на примере одной сцены.

## 10. Основания проверки встроенного API

Проверялись именно возможности Godot, а не работоспособность ещё не написанных методов игры:

- [ProjectSettings Godot 4.4.1](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/ProjectSettings.xml): размеры viewport, stretch, renderer и фильтр; [Window](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/Window.xml): `min_size` и ограничение окна.
- [Node](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/Node.xml), [Signal](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/Signal.xml), [Input](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/Input.xml), [CharacterBody2D](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/CharacterBody2D.xml) и [TileMapLayer](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/TileMapLayer.xml).
- [FileAccess](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/FileAccess.xml), [JSON](https://github.com/godotengine/godot/blob/4.4.1-stable/doc/classes/JSON.xml) и [правила экспорта](https://github.com/godotengine/godot-docs/blob/4.4/tutorials/export/exporting_projects.rst): обычные JSON-файлы нужно явно включить в экспорт; после разбора JSON численные поля требуют проверки и приведения типа.
- [Рекомендации Godot по Git](https://github.com/godotengine/godot-docs/blob/4.4/tutorials/best_practices/version_control_systems.rst).
