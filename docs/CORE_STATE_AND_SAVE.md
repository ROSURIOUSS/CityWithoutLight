# CORE-01: общее состояние и сохранения

Реализация задачи `CORE-01`. Документ описывает **существующий код** и то, как им
пользуются другие модули. Канонические требования остаются в
[INTEGRATION_CONTRACT.md](../INTEGRATION_CONTRACT.md) (разделы 3–4) и
[PROJECT_ARCHITECTURE.md](../PROJECT_ARCHITECTURE.md); это не вторая копия контракта,
а отчёт о реализации и дополнение к нему, которое должен утвердить архитектор.

## 1. Файлы

| Файл | Назначение |
|---|---|
| `scripts/core/game_state.gd` | Единственный источник общих фактов игры. Автозагрузка `GameState` (регистрирует интегратор в `INT-CORE-01`). |
| `scripts/core/save_service.gd` | Один игровой слот в `user://`, проверка и безопасная запись. Автозагрузка `SaveService`. |
| `tests/core/core_test.gd`, `tests/core/core_test.tscn` | Самостоятельные тесты: состояние создают сами, автозагрузок не требуют. |
| `scripts/core/*.gd.uid`, `tests/core/core_test.gd.uid` | UID скриптов, которые Godot требует для отслеживаемых файлов. |
| `.github/workflows/core-01.yml` | Проверка CORE-01 на официальном Godot 4.4.1 в CI (см. раздел 8). |

`project.godot` **не изменялся**: автозагрузки — задача `INT-CORE-01` интегратора.
Скрипты намеренно не имеют `class_name`, чтобы имя автозагрузки не конфликтовало.

## 2. `GameState`

`extends Node`, без `class_name`. Внутренние словари и массивы другим модулям
недоступны по контракту — используйте только методы ниже.

| Метод / сигнал | Поведение |
|---|---|
| `signal state_changed()` | После успешного изменения данных. Операция без изменения сигнал не выдаёт. |
| `reset_new_game() -> void` | Очищает флаги, отношения и хранилища модулей, группа становится `['hero']`. Всегда выдаёт один `state_changed`. |
| `get_flag(id: String) -> bool` | Неизвестный или пустой ID — `false`. |
| `set_flag(id: String, value: bool) -> void` | Пустой ID игнорируется. Сигнал только при реальном изменении. |
| `get_relation(id: String) -> int` | По умолчанию `0`; пустой ID — `0`. |
| `change_relation(id: String, delta: int) -> int` | Ограничивает сумму диапазоном `-100…100`, возвращает итог. Пустой ID — `0` без изменений. Отношение, ставшее `0`, не хранится. |
| `get_party() -> Array[String]` | Копия упорядоченного состава; первый элемент всегда `hero`. |
| `add_party_member(id: String) -> bool` | `false` для пустого ID, `hero` и уже добавленного участника. Дубликатов нет. |
| `export_state() -> Dictionary` | Глубокая копия данных в формате раздела 3. |
| `import_state(data: Dictionary) -> bool` | Сначала полностью проверяет данные, затем заменяет состояние и выдаёт один `state_changed`. При ошибке ничего не меняется и сигнала нет. |
| `get_module_data(module_id: String) -> Dictionary` | Глубокая копия хранилища одного модуля или `{}`. |
| `set_module_data(module_id: String, data: Dictionary) -> bool` | Заменяет хранилище модуля; неизвестный ID или несериализуемые значения отклоняются. |
| `has_module_data(module_id: String) -> bool` | Есть ли данные у модуля. |

Константы: `HERO_ID = "hero"`, `RELATION_MIN = -100`, `RELATION_MAX = 100`,
`MODULE_IDS = ["quests", "inventory", "characters", "location"]`.

### 2.1. Формат `export_state()` / `import_state()`

```json
{
  "flags": {"story.mira.helped": true},
  "relations": {"npc.mira": 1},
  "party": ["hero", "companion.mira"],
  "modules": {"quests": {"quest.mira": {"state": "active"}}}
}
```

- `flags`, `relations`, `party` обязательны и проверяются так, как требует раздел 3 контракта.
- `modules` **необязателен** и появляется в экспорте только когда им пользуются.
  Ключи — только значения из `MODULE_IDS`, значения — `Dictionary` из обычных
  JSON-значений (`null`, `bool`, целое, конечное число, строка, массив, словарь с
  непустыми строковыми ключами).
- Числа из JSON приходят как `float`: целые значения в допустимом диапазоне
  принимаются и приводятся к `int`, дробные и `INF`/`NAN` отклоняются.
- Пустое состояние (`{}`) не является валидным: три обязательных поля нужны всегда.

### 2.2. Расширение `modules`

Это **дополнение к контракту**, предложенное CORE-01, а не его изменение: три
обязательных поля и формат версии 1 не меняются, старые файлы читаются, MVP-код может
его не использовать. Назначение — дать квестам, инвентарю и характеристикам общий
слот хранения без изобретения их API:

- `quests` — состояние квестов (`{"quest.mira": {"state": "active", "step": 2}}`);
- `inventory` — предметы и количество (`{"item.medkit": 3}`);
- `characters` — характеристики персонажей (`{"hero": {"might": 4}}`);
- `location` — идентификаторы локации и точки появления, если системе мира понадобится
  хранить их в общем состоянии, а не только в снимке (см. раздел 4).

Модуль-владелец сам решает, что внутри: CORE-01 проверяет только сериализуемость и
возвращает копии. Логику квестов, инвентаря и боёв здесь реализовывать нельзя.

## 3. `SaveService`

| Метод | Поведение |
|---|---|
| `save_game(snapshot: Dictionary, path: String = "user://save_v1.json") -> int` | `OK` (0) при успехе, иначе код ошибки Godot (`ERR_INVALID_DATA`, `ERR_UNAUTHORIZED`, `ERR_FILE_CORRUPT`, ошибка `FileAccess`/`DirAccess`). Игровое состояние не меняется. |
| `load_game(path: String = "user://save_v1.json") -> Dictionary` | `{"ok": bool, "data": Dictionary, "error": String}`. При успехе `data` — проверенный снимок, `error` пуст. При ошибке `data` пуст, `error` объясняет причину и, если есть `.bak`, указывает его путь. Игровое состояние не меняется. |

Константы: `DEFAULT_SAVE_PATH = "user://save_v1.json"`, `SAVE_VERSION = 1`,
`TEMP_SUFFIX = ".tmp"`, `BACKUP_SUFFIX = ".bak"`.

### 3.1. Формат снимка (версия 1)

```json
{
  "version": 1,
  "world": {
    "id": "world.demo",
    "player_position": {"x": 80.0, "y": 48.5},
    "spawn_point": {"x": 24.0, "y": 24.0}
  },
  "game_state": {
    "flags": {"story.mira.helped": true},
    "relations": {"npc.mira": 1},
    "party": ["hero", "companion.mira"]
  }
}
```

Обязательно: `version` = поддерживаемая версия, `world.id` — непустая строка,
`world.player_position.x/.y` — конечные числа, `game_state` — данные раздела 3.
Дополнительные ключи верхнего уровня и внутри `world` (`spawn_point` в примере)
разрешены и сохраняются, если они сериализуемы: так мир позже сможет хранить точку
появления без смены версии формата. Состояние `game_state.party` дополнительно
проверяется `GameState.import_state`, включая то, что первым идёт `hero` — это
инвариант состояния, а не формы файла.

### 3.2. Безопасная запись

1. Снимок проверяется; при ошибке возвращается `ERR_INVALID_DATA`, файл не трогается.
2. Пишется `<путь>.tmp` (`FileAccess.WRITE`), затем `flush()` и закрытие.
3. Временный файл читается заново и проверяется (`ERR_FILE_CORRUPT` при расхождении).
4. При наличии слота он переименовывается в `<путь>.bak` (предыдущий `.bak` удаляется).
5. `.tmp` переименовывается в слот. Если переименование не удалось, `.bak` возвращается
   на место слота, а `.tmp` удаляется.

Запись разрешена только в `user://` без `..`; попытка писать в `res://` или по
абсолютному пути даёт `ERR_UNAUTHORIZED`. Резервная копия не удаляется после успешной
замены и остаётся доступной для восстановления:

```gdscript
var result := SaveService.load_game("user://save_v1.json.bak")
if result["ok"]:
    # Main сам решает, применять ли восстановленный снимок
    pass
```

Автоматического восстановления из `.bak` нет намеренно: решение принимает `Main`,
чтобы загрузка никогда не подменяла состояние молча.

### 3.3. Ошибки чтения

`load_game` возвращает `ok = false` для отсутствующего файла, нечитаемого файла, не
JSON-объекта, отсутствующей/дробной версии, неподдерживаемой версии (сообщение называет
её), неверной структуры и значений вне диапазона. Файл при этом не перезаписывается и
не мигрируется. Тесты используют отдельный путь `user://save_test_v1.json` и не
затрагивают игровой слот.

## 4. Как пользоваться другим модулям

История (`STORY-01`):

```gdscript
# Последствия выбора применяются только через GameState.
if not GameState.get_flag("story.mira.helped") and not GameState.get_flag("story.mira.refused"):
    GameState.set_flag("story.mira.helped", true)   # сначала флаг, потом остальное
    GameState.change_relation("npc.mira", 1)
    GameState.add_party_member("companion.mira")
```

Мир/бой (`WORLD-01`, `BATTLE-01`): состав берётся копией, чтобы изменения боя не
меняли состояние — `var party: Array[String] = GameState.get_party()`.

Квесты/инвентарь/характеристики: `GameState.set_module_data("quests", data)` и
`GameState.get_module_data("quests")`. Читать и изменять нужно копию и записывать
её обратно; прямой доступ к внутренним словарям запрещён.

Локация и точка появления: в архитектуре позиция игрока и ID мира собираются в
`Main` и попадают в раздел `world` снимка. Своей копии в `GameState` они не имеют,
чтобы не появилось второе хранилище позиции. Если мир решит хранить «логическую»
локацию (ID комнаты) между сценами, для этого есть `modules.location`.

`Main` (интегратор) при сохранении и загрузке:

```gdscript
# Сохранение (только в режиме исследования, F2)
var snapshot := {
    "version": SaveService.SAVE_VERSION,
    "world": {
        "id": world.get_world_id(),
        "player_position": {"x": world.get_player_position().x,
                            "y": world.get_player_position().y},
    },
    "game_state": GameState.export_state(),
}
var code := SaveService.save_game(snapshot)          # OK или код ошибки
# Загрузка (F3): сначала проверка файла, потом состояние.
var loaded := SaveService.load_game()
if loaded["ok"]:
    var previous := GameState.export_state()
    if GameState.import_state(loaded["data"]["game_state"]):
        if not world.set_player_position(...):
            GameState.import_state(previous)         # откат, если позиция не принята
    # при неудаче import_state состояние уже не изменилось
# иначе показать loaded["error"] в Status и оставить игру как есть
```

## 5. Проверки

Тест проверяет, в частности: создание нового состояния и значения по умолчанию;
флаг (установка, повтор, снятие, пустой ID) и точное число сигналов; ограничение
отношений; группу без дубликатов и независимость копии `get_party()`; независимость
`export_state()`; атомарный отказ `import_state` (10 видов неверных данных);
хранилища модулей и отказ для `Node`/`Vector2`; запись и чтение тестового слота;
отсутствующий файл; повреждённый JSON; неверную структуру; отношение вне диапазона;
неподдерживаемую версию; отказ записи в `res://`; сохранность предыдущего слота и
содержимое `.bak`. Тестовые файлы удаляются в конце.

```sh
godot --headless --path . --import
godot --headless --path . res://tests/core/core_test.tscn
```

Сцена завершается `get_tree().quit(0)` при успехе и `quit(1)` при ошибке, поэтому
проверять нужно код возврата, а не только отсутствие зависания.

Фактический результат: на официальном Godot 4.4.1 в CI тестовая сцена сообщила
`CORE-01: 108 checks passed.`; импорт проекта, проверка `.uid` и тесты BASE-01 прошли.
Строки `ERROR: Parse JSON failed` в логе ожидаемы — их печатает сам Godot при разборе
намеренно повреждённых тестовых файлов. Локально Godot в среде исполнителя не
запускался: скачать официальный архив было невозможно, поэтому прогон выполнялся в CI.

## 6. Известные ограничения и предложения архитектору

1. **`modules` — расширение контракта.** Нужно решение архитектора: внести
   `get_module_data`/`set_module_data`/`has_module_data` и необязательное поле
   `modules` в раздел 3 контракта (сохранение остаётся версии 1) либо отложить это
   до `POST-01`. Код MVP от расширения не зависит.
2. **Дублирование проверок.** `SaveService` не вызывает `GameState` по контракту,
   поэтому структурная проверка `game_state` (типы, диапазон отношений) повторяет
   правила раздела 3. Альтернатива — разрешить `SaveService` вызывать статическую
   функцию-валидатор `GameState`; это изменение контракта.
3. **Инвариант `hero` первым** проверяет только `GameState.import_state`. Снимок с
   группой без `hero` пройдёт `load_game` и будет отклонён на импорте; `Main` обязан
   обработать `false` и не менять позицию.
4. **Атомарность.** Запись через временный файл и переименование безопаснее прямой
   записи, но поведение файловой системы при сбое питания различается — абсолютная
   атомарность не обещается.
5. **UID.** Godot в среде разработки CORE-01 запустить не удалось, поэтому файлы
   `.gd.uid` созданы по алгоритму `core/io/resource_uid.cpp` Godot 4.4.1 (13 символов,
   алфавит `a…y0…8`). CI при импорте проверяет их и может нормализовать.
6. **Не проверено вручную.** Графический запуск, фактические диалоги/бой/история,
   миграция старых слотов (их ещё не существует) и экспорт сборки к CORE-01 не
   относятся и здесь не проверялись.
